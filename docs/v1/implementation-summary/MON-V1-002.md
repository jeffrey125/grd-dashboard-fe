# MON-V1-002 implementation handoff

## Summary

Staff can restart a completed delivered Shipment with a future follow-up date from
desktop row actions, mobile cards or detail. Monitoring continues until that date
starts in New York time. Carrier delivery information remains visible.

## Changes Made

- Added a shared MUI Monitor again dialog, defaulting to tomorrow and requiring a
  future date. It uses the existing authenticated follow-up PATCH and query
  invalidation for list, details and overview. Disabled carriers are explained.
- Added list/mobile/detail controls and stopping-date guidance. Expired delivery
  windows disable refresh/resume while worker state reconciliation catches up.
- Use React Hook Form's dirty baseline for assignment edits: actual drafts survive
  external changes, pristine forms follow server updates, and successful saves
  reset the baseline. This fixes a real-browser failure where an external clear
  incorrectly disabled Monitor again as if the old date were a staff draft.
- Exclude known deliveries from the Upcoming response invariant independently of
  active monitoring; align staff wording and contract documentation with the backend.
- Reuse installed MUI, TanStack Query, Zod, Day.js and React Hook Form. No dependency,
  lockfile, schema, deployment or container configuration changes.

## Review Notes

The backend is authoritative for New York calendar dates, state and pre-lookup
cutoffs. The dialog uses the same business timezone and defaults to tomorrow;
manual pauses and carrier disablement retain their existing behavior. Staff can
save a future follow-up without enabling a disabled carrier. Unsaved detail drafts
must be resolved before opening Monitor again.

State/tab expiry changes reconcile on the worker's next scan; logical carrier
lookups independently recheck the deadline. No claim of live provider verification.

Both servers were left running and verified reachable:

- Frontend: `http://localhost:5173/shipments?tab=delivered` (HTTP 200).
- Fixture API: `http://localhost:3018/api/v1/health/ready` (application/database up).
- Test login: `frontend-staff@example.test` / `staff fixture password`.

The API uses a disposable fixture database and has the tracking worker disabled.
Manual edits affect test records only. Startup commands from the frontend repo:
`FE_TEST_API_PORT=3018 node scripts/auth-backend.mjs` and
`VITE_API_ORIGIN=http://localhost:3018 pnpm exec vite --host localhost --port 5173 --strictPort`.
